Permission popup decision (2026-09-14): offer "Approve Once" for one exception,
"Approve for this session" for the current conversation's eight-hour session,
and "Reject". Lasting grants are edited in conversation, project, or agent
settings. MiniClaw must enforce the grant lifetime; the current native MCP
elicitation response only accepts or declines and does not carry an expiry.
Scoped agents may execute commands, but the exact command and working directory
must be reviewed by the user before every newly requested execution. A session
approval must not silently authorize different command text. A MiniClaw-controlled
command tool is implemented in source because current Codex on-request approval does not prove
that every command prompts. The user approved command execution only through that
reviewed path; direct GUI control of Terminal and Script Editor is unavailable to
scoped agents. This applies to shell and AppleScript commands. Exact command text,
working directory, agent, conversation and machine identify a session grant; edited text
or a different directory requires another decision. The eight-hour expiry is
absolute, survives backend restart without renewal, and can be revoked early.

Agent and project permissions are inherited defaults. Either can grant an app or
file; conversation settings may add an explicit grant or block an inherited one.
The conversation's explicit choice wins. Removing one source stops later actions
only when no other source still allows them. Settings show the effective permission
and its sources. A permission change takes effect at the next dispatch, rejects
queued work, and attempts to stop active work; it cannot undo a completed native
action. Approval requests bind the exact operation, agent, conversation, machine,
and turn. A model message, native helper prompt, or guest-originated HTTP request
cannot edit permission records or approve its own request.

#### Resource admission

The 50/50/25 defaults apply globally, including the backend and all workspace VMs.
They are allocation ceilings, not a promise about total CPU utilization or host
resident memory. Supervisor overhead, graphics and unrelated host processes also
consume resources. Report observed usage separately from reserved capacity.

Use host CPU count and physical RAM, not the smaller capacities reported inside the
backend VM. Round fractional CPU capacity down. CPU/RAM reservations include starting,
running, paused and stopping guests; release only after confirmed stop. Creation of a
stopped VM consumes disk budget; starting it additionally requires compute capacity.
Check creation, startup, resume, resize and import. Stopping a VM never releases disk.

Reserve each virtual disk's maximum size, not just its current sparse-file allocation.
Include auxiliary storage, retained images, snapshots and backups against the relevant
storage budget without double counting. Check actual free space separately; a 25%
ceiling does not guarantee that capacity is available. Multiple volumes and APFS shared
containers require measured capacity identities before external-storage support.

The host supervisor must serialize admission, persist reservations, and reconcile
actual VM ownership after crashes. Two starts cannot both consume the same remainder.
Unknown state retains its reservation until reconciled. Failed operations release only
resources proven unused; retained partial disks still count. Lowering limits must not
kill VMs or delete files. Show excess usage, refuse further increases, and allow stops,
deletions and reductions. UI reports capacity, reservations and the blocking resource.

`scripts/experiments/vm-resources.swift` is an isolated tested calculator for a proposed
inventory, not that supervisor or a live limiter. Its caller supplies validated host
measurements, complete reservations and additional disk usage. Durable accounting,
live collection, concurrency and UI integration remain to implement and test.

## Product decisions

- Standalone operation: MiniClaw starts and owns its background Codex App Server process. Users can initiate ChatGPT OAuth from MiniClaw without opening or signing into the Codex desktop app first. Checking persisted authentication is only for avoiding repeated OAuth after authorization, not detecting or attaching to an open desktop session. The Codex executable is a runtime dependency; the desktop GUI is not. Shared versus isolated credential storage is distinct from this process independence; the user's latest clarification does not explicitly choose a new storage policy.
- Target: a browser app for one local user. Authentication and inference still require internet access.
- Scope: conversations with Codex using a ChatGPT account. This is not a mirror of ChatGPT website conversations, a general ChatGPT subscription dashboard, or API organization billing.
- Tasks: create and select Codex tasks in MiniClaw's controlled workspace. The shared Codex home can contain other tasks; filter by workspace and leave unrelated desktop/CLI history alone.
- Account: reuse the existing local Codex ChatGPT OAuth session and its subscription. There is no MiniClaw account, password, signup, separate credential profile, or routine login gate. Offer Codex-managed OAuth only when `account/read` reports that sign-in is needed. Task history is local Codex data, not cloud account-scoped storage; authentication loss hides it without deleting it.
- Responses: text and safe Markdown, with visible completed, stopped, failed, and reconnecting states.
- Concurrency: one active turn per task; different tasks may run independently. Selecting another task does not stop the first one.
- Model: discover the full OAuth-backed Codex catalog with paginated `model/list`, including hidden entries. Let the user choose a model and one of its advertised reasoning efforts. This supersedes the original no-picker scope. New selections use the selected model's default effort. Settings apply per task/turn, never through shared config writes. Catalog inclusion is not a guarantee that a later inference request will be accepted by the service.
- Out of scope: API-key mode, attachments, voice, general tool approval UI, arbitrary workspaces, remote hosting, multi-user access, billing changes, credit purchases/redemption, branching, and editing previous messages. Computer-app confirmation prompts are now in scope.

## Architecture and startup

```text
Browser: Svelte + TypeScript
          | same-origin HTTP + SSE
          v
Rust: Axum routes, account state, task state, event buffers
          | private stdin/stdout, long-lived JSON-RPC
          v
Owned Codex App Server -> ChatGPT auth and Codex services
          |
          +-> existing Codex credentials and task history
```

`npm start` builds Svelte and Rust, then runs the backend. Axum serves `web/dist`
and `/api` on one loopback origin. The browser calls relative URLs. Reserve `/api`
before the SPA fallback so API errors never return HTML.

`npm run dev` adds Vite's [build watcher](https://vite.dev/guide/build.html#rebuild-on-files-changes),
which writes assets without an HTTP or hot-reload server. Refresh the browser after
a frontend change; restart for Rust/config changes. Direct Vite dev/preview commands
are rejected at server creation, while builds and type checks can load the config.

Before binding or launching Codex, acquire an exclusive OS file lock in MiniClaw's
data directory. Keep the descriptor open for the backend lifetime; the OS releases
it on process exit. A duplicate instance or occupied port exits without choosing
another port. Tests may use separate temporary data directories and loopback ports.
This uses Rust's [File::try_lock](https://doc.rust-lang.org/std/fs/struct.File.html#method.try_lock),
with no additional crate or stale-PID-file mechanism.

Codex uses `app-server --listen stdio://`, with no second network listener. There
is no connect mode, port 4500, dev-origin override, or public host option in this
setup. A future transport change requires a new review. Browser OAuth may briefly
use Codex's own [loopback callback listener](https://github.com/openai/codex/blob/main/codex-rs/login/src/server.rs);
it is not a persistent app port. Normal chat still requires outbound internet access.

| Setting | Default / behavior |
| --- | --- |
| `MINICLAW_PORT` | `8787`; bind only `127.0.0.1` |
| `CODEX_BIN` | The installed application path above; actionable error if missing |
| `MINICLAW_DATA_DIR` | macOS user application-data directory, under `MiniClaw` |
| `CODEX_HOME` | Inherit the user's configured Codex home, or let Codex use its normal default; do not redirect production auth into MiniClaw's data directory |

### Current transport

The adapter owns the child and transport, a bounded outbound channel, a monotonically increasing request ID, and a pending-request map of IDs to one-shot response senders. A reader loop processes responses, notifications, and server requests independently of HTTP lifetimes.

For stdio, frame messages as newline-delimited JSON and drain stderr independently so a full pipe cannot stall the child. Bound frame sizes, report malformed/oversized frames, and redact stderr before logging. Remove timed-out entries from the pending map; a late response must not complete a newer request.

1. Open transport, send `initialize` with MiniClaw client metadata, await success, then send `initialized` exactly once per connection.
2. Mark the connection ready only after initialization. Match replies by ID; tolerate unrelated notifications and unknown optional fields.
3. Apply a 30-second default RPC response timeout. That timeout ends waiting for acknowledgement, not an active model turn. Bound pending calls and outbound frames.
4. Reject pending calls on disconnect. Reinitialize on reconnect and restore subscriptions for tasks this backend had loaded, using resume and history reconciliation.
5. Retry safe reads after reconnection. Never automatically repeat login creation, task creation, or `turn/start` after an ambiguous send.
6. Handle server-initiated approval, elicitation, and user-input requests with schema-correct refusal/cancellation responses. Return a structured unsupported-method error for unknown requests; do not leave them hanging.

Use generated schemas and fixture tests for the selected protocol subset; do not maintain a browser-accessible generic JSON-RPC proxy. Generate public API TypeScript types from Rust DTOs with a small tool such as `ts-rs`, and runtime-validate external input at the Rust boundary.

For chat behavior, start/resume with explicit read-only sandboxing and a non-escalating approval policy. Disable shell execution and web search using supported configuration; disable other execution paths, integrations, and inherited hooks identified by the effective-config probe. Read-only sandboxing still permits reads, and an approval policy is not a tool-disable switch. ## Sending, streaming, and recovery

Each task maintains a reducer keyed by `(threadId, turnId, itemId)`, an active-turn state, and a bounded replay ring. The global feed has its own ring. Use event IDs of `<backend-epoch>:<sequence>` so a backend restart cannot be mistaken for a continuation of old events.

The task feed exposes typed events: `turn.started`, `message.delta`, `message.completed`, `turn.completed`, `turn.error`, and `resync.required`. Include task/turn/item IDs as appropriate. Global events carry connection, account, usage, login, and task-summary changes. Do not forward raw reasoning, tool payloads, or credentials.

Begin each fresh global subscription with an atomic current-state snapshot and cursor, then live events. After a replay gap, send a replacement snapshot so missed login or usage updates cannot leave the UI stale. Account-generation changes take precedence over all older snapshots and events.

- Capture notifications as soon as a task is created or resumed, even before a browser subscribes.
- Build the local snapshot and its cursor atomically with reducer updates. Subscribe after that cursor, replay the gap, then continue live. Buffer notifications during initial history hydration before publishing a consistent snapshot.
- Support `Last-Event-ID` on automatic reconnect and `after` for a new EventSource after a snapshot. Ignore repeated event IDs in the frontend.
- Append deltas only to their matching message item. On `item/completed`, replace that item's text with its canonical final text rather than appending it again. Multiple assistant items in one turn stay distinct.
- Treat `turn/completed` as the terminal authority. Keep Stop pending until completion/reconciliation; preserve partial output after interruption or failure. An upstream `error` with `willRetry` remains a recoverable state.
- Bound each ring by both count and bytes, initially 2,000 events or 2 MiB, and cap combined buffers at 16 MiB. Evicted/gapped cursors get `resync.required`; the UI fetches a new snapshot. Reconcile upstream history after a transport gap, then start a new event epoch for affected feeds.
- Send SSE keepalive comments every 15 seconds. Disconnect slow subscribers with a resync path rather than blocking the Codex reader. Apply idle-task eviction without removing active turns.

Take a per-task lock before sending and reserve the pending slot before writing to Codex. Two tabs sending together must yield one accepted turn and one busy response; do not let an extra `turn/start` implicitly steer an existing response.

Use a browser-generated UUID as `clientMessageId` and map it to the installed protocol's `clientUserMessageId`; persisted user items expose `clientId` for reconciliation. Repeated identical requests within the backend lifetime return the known receipt. Reject reusing an ID with different text. This is local deduplication, not a claim that Codex guarantees idempotency.

If transport fails after a write, show "Checking whether your message was sent" and reconcile history by client ID before allowing retry. Keep the draft until acceptance is known. If history cannot establish the outcome, show "Send status unknown" and require a deliberate retry after the user can inspect history. Do not promise exactly-once delivery across backend crashes.

  transfer code. No whole-disk backups in this version, so the running-disk question does not
  arise.
- **Schedule:** Off (default), Daily or Weekly, per VM, plus "Back up now". A schedule runs
  only while MiniClaw runs and the VM is running; it never starts a VM. A missed run happens
  at the next chance.
- **Retention:** newest 3 by default, 1 to 10. Older backups go to the Trash after a new one
  succeeded, never before.
- **Failure:** three retries after the first attempt, then a notification.

## Delegation, activity and scheduled runs decision (2026-09-21)

Status: built and tested against the fake Codex on 2026-09-21; not observed with real model
calls. Two points I settled without asking: MiniClaw does not start a parent turn by itself
when a background run finishes (the parent agent gets the result with the user's next message),
and at first only Codex conversations could delegate; Claude conversations can since the
same day, observed with the real CLI.

- **Wait or background is the user's choice, every time.** Each delegation pauses for a small
  prompt: "Wait for it" or "Run in background". Nothing starts before the answer.
  - Wait: the parent's turn pauses, gets the result as the tool's answer and carries on.
  - Background: the parent's turn carries on at once. The result arrives later in the parent
    conversation as its own message.
- **A delegated agent's words are labelled with its name**, never shown as the parent speaking.
- **Limits are set per agent:** how many delegations a parent turn may make and how long one
  may run. Defaults: 3 and 10 minutes. A delegated agent cannot delegate further.
- **Approvals** from a delegated run appear in the parent conversation and name the delegated
  agent. The recipient's own rules apply; the parent's permissions are never lent to it.
- **Visibility:** the parent shows a "Delegated to <agent>" block with status, time and
  result, expandable to the run's transcript. A button moves the run into its own
  conversation to continue with that agent. Runs do not appear in the conversation list
  otherwise.
- **Activity tracker, all chats:** every turn shows a live, collapsible list of what
  MiniClaw's own tool did: folders listed, searches, files read, commands with output and
  exit code, and writes and edits as coloured diffs, compact with an expand arrow.
- **Automatic runs:** schedules only. A saved prompt for one agent in one project, hourly,
  daily or weekly, off by default, with visible state, last result and "Run now".
- **Unattended approvals:** a request waits for a configurable time. With no answer the run
  is terminated, not left waiting or running.

## Workspace panel and coding session decision (2026-09-21)

Status: built on 2026-09-21. The coding session is observed with real Codex and Claude models;
the panel is tested against a real git repository. The VM path of Files and Changes uses the
existing worker and is not observed with a real VM. See
[docs/coding-session](docs/coding-session/README.md) and
[docs/workspace-panel](docs/workspace-panel/README.md).

### The right-hand panel

- It replaces the fixed VM desktop column. It is a **resizable side panel** with tabs across
  its top, and it **collapses to a thin rail** of icons so the chat gets the full width. Drag
  its left edge to resize. It remembers its width, its tab and whether it is collapsed. On a
  narrow window it is a full-width sheet opened from a button.
- Tabs: **VM** (the live desktop that exists today, only for a VM conversation), **Files**,
  **Changes**, **Activity** (the conversation's tool activity in one place).
- **Files:** a tree of the working folder with a read-only viewer: syntax colours, line
  numbers, a marker on changed files and "open in Changes". Large or binary files show their
  size. Nothing is edited here.
- **Changes** shows the **git working tree**: each changed file with `+added -removed`, and a
  red and green diff when opened. Where there is no repository, it falls back to what the
  agent changed in this conversation, from MiniClaw's own record, and says so.
- Git actions in the first version: **view**, and a confirmed **Discard** per file (restore a
  tracked file; move a new untracked file to the Trash). No staging, commit or push.
- **Diffs** are unified by default with line numbers and syntax colours, with a switch to
  side-by-side on a wide window; the choice is remembered.
- **Files, Changes and the coding session work in VM conversations from the start**, through
  the VM worker. That needs new worker code, so `miniclaw update-vm` and the guest installer
  must be run before it can be used in a VM.

### Coding session

- A **toggle in the composer, per conversation**, next to Computer Use and skills. While on,
  the conversation shows a strip "Coding session: every change is reviewed". It can be
  switched at any time. A project can set it on by default for its new conversations.
- While on, **every file write, every edit and every shell command stops for the user**, even
  where a saved rule would allow it.
- A write or edit opens a **review popup with a scrollable, GitHub-style diff** of exactly
  what would change. Nothing is written before the user decides.
- Decisions: **Apply**; **Reject**; **Reject with a note** that goes back to the agent as the
  reason; **Edit the proposed text** before applying, in which case what the user applied is
  written and the agent is told the file differs from its proposal; **Apply all remaining in
  this turn**.
- A waiting review **waits up to 30 minutes**, then is rejected; the agent is told nobody
  reviewed it and a notification records it. Stop ends it at any time.
- The user asked that this UI "actually look good and feel nice to read from and use", built
  with the rules of the front-end skill.
